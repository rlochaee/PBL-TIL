# 📘 Today I Learned

### 1. 오늘 배운 내용
오늘 미션에서는 객체지향 언어인 자바의 구조와 관계형 데이터베이스의 물리적 테이블 구조 사이의 차이점을 파악하고 이를 연결하는 방법을 학습했다.

자바 코드에서는 참조 필드와 리스트(List)를 활용해 객체 간의 양방향 연결이 가능하지만, MySQL 데이터베이스에는 리스트 개념이 존재하지 않으며 오직 N(다) 쪽 테이블에 외래 키(FK) 컬럼을 생성해 관계를 맺는다는 규칙이 존재한다.

JPA는 이러한 자바 객체 구조와 데이터베이스 테이블 구조를 중간에서 매핑해 주는 역할을 하며, 개발자가 SQL을 직접 작성하지 않고 객체 단위로 데이터를 다룰 수 있도록 지원한다. 또한 복합적인 데이터 변경 작업 시 발생할 수 있는 데이터 불일치 문제를 방지하고 데이터의 일관성을 유지하기 위해 여러 DB 작업을 하나의 단위로 묶어 관리하는 트랜잭션의 역할을 배웠다.


### 2. 핵심 정리 (내 언어로)
- @ManyToOne과 @OneToMany (다대일과 일대다 매핑)
    과제 엔티티처럼 N(다)의 위치에서 상대 엔티티를 단일 객체로 참조할 때는 @ManyToOne을 사용하고, 회원 엔티티처럼 1(일)의 위치에서 여러 과제 객체를 리스트 형태로 참조할 때는 @OneToMany를 사용

- 연관관계의 주인과 mappedBy (외래 키 관리 권한 설정)
    데이터베이스의 테이블 구조상 외래 키(FK) 컬럼은 무조건 N(다) 쪽 테이블에 생성되므로, 실제 외래 키를 가지는 과제 엔티티가 연관관계의 주인이 됨 주인이 아닌 회원 엔티티에는 mappedBy 속성을 지정하여 해당 필드가 읽기(조회) 전용임을 설정

- @JoinColumn (외래 키 컬럼 명시)
    연관관계의 주인인 엔티티에서 데이터베이스 테이블에 생성될 외래 키 컬럼의 이름을 직접 지정

- 외래 키(Foreign Key)의 생성 위치
    관계형 데이터베이스의 규칙에 따라, 1:N 관계에서는 데이터의 중복과 테이블 구조의 변형을 막기 위해 항상 수량이 더 많이 발생하는 N(다) 쪽 테이블에 외래 키 컬럼이 생성되어야 함

- @Transactional (트랜잭션 적용)
    서비스 계층의 메서드가 실행될 때 내부의 여러 데이터베이스 작업을 하나의 작업 단위로 묶어주는 기능
    도중에 에러가 발생하면 이전에 성공한 작업까지 모두 취소(Rollback)하여 데이터가 비정상적으로 저장되는 것 방지

- @Transactional(readOnly = true) (읽기 전용 최적화)
    데이터를 수정하지 않고 조회만 하는 메서드에 이 옵션을 적용하면, JPA 내부의 변경 감지 기능이 작동하지 않아 메모리 사용량이 절약되고 조회 속도가 향상

### 4. 느낀 점
이번 미션에서는 연관관계 매핑을 통해 그동안 파편화되어 존재하던 회원 데이터와 과제 데이터를 하나의 유기적인 흐름으로 연결하는 방법을 배웠다. 자바의 객체 참조 구조와 관계형 데이터베이스의 외래 키 규칙을 @ManyToOne과 @OneToMany 어노테이션으로 매핑해 보며 두 기술의 구조적 특징을 알 수 있었다. 특히 양방향 관계를 설정할 때 주인이 아닌 엔티티에 mappedBy를 지정하여 데이터베이스 테이블에 불필요한 컬럼이 중복 생성되는 현상을 막는 올바른 설계법을 터득했다. 또한 데이터 변경 작업 시 원자성을 보장해 주는 @Transactional을 서비스 계층에 필수적으로 적용해야 하는 실무적 이유와 안정성의 중요성을 배웠다. 또한, 조회 메서드에 readOnly = true 옵션을 적용해 보면서 서버의 메모리와 조회 성능까지 고려하는 것의 필요성을 알 수 있었다!

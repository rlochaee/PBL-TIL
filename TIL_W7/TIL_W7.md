# 📘 Today I Learned

### 1. 오늘 배운 내용<강의영상>
1. 스프링 부트 어노테이션 역할
    @Controller: 이 클래스가 웹 요청을 받는 문지기라고 스프링에 등록

    @ResponseBody: HTML 파일 대신, 메서드가 리턴하는    데이터 알맹이(텍스트/JSON)를 보냄

    @GetMapping: 클라이언트의 조회(GET) 요청 주소를 감지해 자바 메서드(액션 메서드)를 실행

2. HTTP 소통 (편지 비유)
    요청(Request): 클라이언트가 편지 겉면에 주소(URL)와 행위(Method)를 적고, 봉투 안에 데이터(Body)를 넣어 서버에 보냄

    응답(Response): 서버는 결과를 상태 코드(성공/실패)로 봉투에 찍고, 답장 데이터(Body)를 담아 돌려줌

3. 왜 String(문자열/JSON)으로 소통할까?
    이유: 기기마다 쓰는 언어(Java, JavaScript, Swift 등)가 달라도, '텍스트(String)'는 전 세계 모든 컴퓨터가 읽을 수 있는 유일한 공통 표준 언어이기 때문
    웹 화면에 데이터를 뿌려주는 API 통신(JSON)을 할 때나, 네이버 같은 웹 페이지(HTML 텍스트)를 불러올 때 사용됩니다.

### 2. 핵심 정리 (내 언어로)
- HTTP 메서드별 역할
    POST: 새로운 자원을 생성할 때 사용 (POST /members/lions ➔ 아기사자 등록)

    GET: 특정 자원을 조회할 때 사용 (GET /members/{name} ➔ 단일 회원 조회)

    PUT: 기존 자원을 전체적으로 수정/교체할 때 사용 (PUT /members/lions/{name} ➔ 정보 수정)

    DELETE: 특정 자원을 삭제할 때 사용 (DELETE /members/{name} ➔ 회원 삭제)

- HTTP 상태 코드의 의미
    클라이언트(Swagger)에게 서버의 처리 결과를 숫자로 정확하게 알려주는 것

    201 Created: 새로운 멤버가 성공적으로 등록
    200 OK: 멤버 조회나 정보 수정 성공
    204 No Content: 멤버 삭제가 성공
    404 Not Found: 수정, 삭제, 조회하려는 대상 멤버 이름이 저장소에 존재하지 않음
    409 Conflict: 이미 존재하는 이름으로 멤버를 또 등록하려 해서 서버 데이터와 충돌했음을 의미

- @PathVariable vs @RequestBody 차이점
    @PathVariable: URL 경로에 포함된 동적인 값을 추출할 때 사용

    예: /members/lions/{name} 경로에서 {name} 자리에 들어오는 글자를 가져옴. (주로 수정, 삭제, 단일 조회 대상 지정에 사용)

    @RequestBody: 클라이언트가 보낸 HTTP 요청 본문(JSON 데이터)을 자바 객체로 변환하여 통째로 받아올 때 사용합니다.

    예: 등록이나 수정할 때 필요한 수많은 필드(major, generation, part 등) 데이터 덩어리를 받아옴.

- DTO(Data Transfer Object) 역할
    도메인 객체 보호: 비즈니스 로직과 핵심 규칙을 담고 있는 도메인 클래스(Role, Lion)가 외부(웹 환경)에 직접 노출되는 것을 막아 보안과 안정성을 높임

    필요한 데이터만 선별 배달: 화면이나 클라이언트가 요구하는 데이터 규격에 딱 맞춰서 데이터를 포장하고 전달하는 배달 상자 역할

- 역할별로 DTO를 분리하는 이유
    요구사항의 차이: 등록할 때는 이름(name)이 필수지만, 수정할 때는 이름이 URL 경로(@PathVariable)로 들어오기 때문에 수정 DTO에서는 name 필드를 제외

    화면 노출용 필드 제어: 도메인 객체에는 없는 "아기사자", "운영진"이라는 글자(roleName)를 화면에 출력해 주기 위해 응답 전용 DTO(LionResponse)를 따로 만들어 관리하는 것이 결합도를 낮춤

- ResponseEntity를 사용하는 이유와 상태 코드 제어
    스프링 컨트롤러에서 단순히 데이터 객체만 리턴하면 무조건 200 OK 상태 코드만 나감 but ResponseEntity라는 포장 클래스를 사용하면, 성공했을 때는 .status(HttpStatus.CREATED)나 .ok()로 성공 코드를 제어하고, 실패했을 때는 .status(HttpStatus.NOT_FOUND) 같은 에러 코드를 자바 코드로 직접 세밀하게 제어할 수 있음

### 4. 느낀 점
- 7주차 미션을 진행하면서 복잡한 요구사항을 REST API 설계 원칙에 맞춰 코드로 구현해보았다. 지침에 따라 도메인과 DTO를 분리하여 roleName 같은 화면 노출용 데이터를 다루고, ResponseEntity로 HTTP 상태 코드를 제어하는 방식을 배우게 되었다. 7주차 미션 도중 아기사자와 운영진 등록 시 중복 이름 검증이 빠져 409 Conflict 처리가 안 되던 문제를 서비스 계층에 이름 확인 로직을 추가해 해결했다. 또한, Swagger 결과 창에 roleName 필드가 누락되는 현상이 있었는데 문제를 찾아보며 도메인에 필드를 추가하는 것이 아니라 응답 DTO(LionResponse) 내부에서 "아기사자" 문자열을 직접 주입해야함을 알 수 있었고 이 과정에서 화면 노출용 데이터는 도메인이 아닌 DTO가 담당해야 한다는 점을 확실히 깨달았다!
